# Demo 验收计划

版本：0.1  
状态：阶段 0 已确认

## 1. 验收目标

Demo 要证明核心体验能够完整演示，而不是证明已经具备医疗诊断或医院生产接入能力。

验收主线：

```text
真实样机连接
→ 实时画面
→ 拍照
→ 绑定牙齿和区域
→ AI 基础报告
→ 可选医生咨询
→ 补拍或复查
→ 进入日历和单颗牙历史
→ 清洁间隔提醒
```

## 2. Demo 范围

当前黑客松 HTML 演示属于“界面与流程原型”，用于证明：

- 上传照片后自动进入模拟 AI 分析；
- 低质量照片停止疾病分类并提示重拍；
- 报告先作为草稿，确认牙齿与区域后才保存；
- 保存后首页、牙齿档案和日历立即同步；
- 新事件进入独立咨询草稿，不沿用旧医生回复；
- USB 摄像头通过系统相机权限显示真实实时画面并可截帧；
- Wi‑Fi 流程继续保持“连接演示”标识。

HTML 演示中的 USB 画面属于真实本地摄像头接入，但不代表 Wi‑Fi 视频、真实 AI 图片识别或医院在线咨询已经接入。

必须演示：

- 演示电脑连接当前真实 USB 摄像头样机；
- 实时观看和拍照；
- 图片质量提示；
- 牙齿画像与牙齿/区域绑定；
- 创建牙齿问题事件；
- AI 可见观察、疑似残留、历史对比、基础疾病初筛判断和建议；
- AI 低质量拒绝或重拍；
- 演示医生咨询、回复和请求补拍；
- 四类记录来源区分；
- 日历、单颗牙和事件历史；
- 清洁间隔提醒；
- App 重启和失败恢复；
- 分享预览与访问隔离。

不要求：

- AI 替代医师完成最终确诊；
- 菌斑检测；
- 干净或不干净结论；
- 正式医院系统连接；
- 临床性能声明；
- Android；
- 大规模云部署。

## 3. 测试环境

阶段 1 开始前记录：

- 样机型号和固件；
- 视频协议和参数；
- iPhone 型号；
- iOS 版本；
- App 构建版本；
- USB 接口、数据线、供电与系统识别名称；
- Wi‑Fi 环境（仅在 Wi‑Fi 样机可用时记录）；
- AI 模型和报告结构版本；
- 演示医生账号；
- 演示数据编号。

不得使用真实患者资料作为默认 Demo 数据。

## 4. 场景 A：连接、实时画面与拍照

步骤：

1. 打开观察页；
2. 插入 USB 样机并确认系统识别；
3. 点击“连接 USB 摄像头”并允许相机权限；
4. 从设备列表选择冲牙器摄像头；
5. 显示实时画面并拍摄清晰照片；
6. 拔插 USB，验证断流提示和恢复。

通过标准：

- 目标环境下连接成功率不低于 95%；
- 目标端到端画面延迟不高于 500ms；若样机限制无法达到，必须记录实测值和体验影响；
- 拍照后原图可查看；
- 断线不丢失已拍照片；
- 重连不产生重复事件；
- 权限拒绝时有清楚恢复路径。
- 多摄像头环境下可以明确选择 USB 样机而不是电脑内置摄像头。

## 5. 场景 B：牙齿画像与事件

步骤：

1. 建立牙齿画像；
2. 选择一颗牙和一个区域；
3. 保存照片并创建事件；
4. 添加第二张照片；
5. 故意选错牙后更正；
6. 关闭 App 再恢复。

通过标准：

- 所有照片、消息和报告绑定同一事件；
- 牙齿更正保留变更历史；
- 身份不确定时允许待整理；
- App 重启后恢复到原事件；
- 不出现跨用户、跨牙齿或跨事件混合。

## 6. 场景 C：AI 报告与图片对比

测试数据：

- 明显疑似食物残留；
- 清洁后同区域照片；
- 多时点同牙照片；
- 不同牙照片；
- 模糊、反光、水滴、过暗和角度差异大照片；
- 可见外观变化但不足以确认原因的照片。

通过标准：

- 从拍照到发起 AI 查看不超过 3 个主要操作；
- 低质量照片给出具体重拍建议；
- 不同牙或不可比照片不生成变化结论；
- 报告显示原始依据、限制、模型版本和 AI 来源；
- 对满足质量要求的样张，能明确输出疑似蛀牙、牙龈发炎、肿胀、牙结石或未发现上述明显特征；
- 每个疾病初筛结果同时显示类别、可见依据、可信程度和下一步；
- 初筛标题清楚，不能只显示“可能需要关注”；
- 初筛结果明确标为 AI 判断；任何最终确诊必须由医师给出；
- 不输出菌斑结论、清洁评分或干净/不干净判断；
- 删除原图后依赖报告进入证据失效状态。

## 7. 场景 D：医生咨询演示

步骤：

1. 从 AI 报告进入“请医生查看”；
2. 预览并选择分享内容；
3. 提交咨询；
4. 医生查看原图和问题；
5. 医生请求补拍；
6. 用户在原事件补拍；
7. 医生回复；
8. 用户结束或设为待复查。

通过标准：

- 未确认前不发送；
- 分享范围与预览一致；
- 重复点击和网络重试只创建一次咨询；
- 医生回复与 AI 报告视觉和数据来源不同；
- 补拍仍属于原事件；
- 医生更正保留前一版本；
- 测试用户区分 AI 与医生来源的正确率不低于 90%。

## 8. 场景 E：日历和多年历史

准备至少覆盖：

- 多年时间跨度；
- 多颗牙；
- 拍摄、清洁、AI、咨询、就医、治疗和复诊；
- 用户、设备、AI 和医院四种来源；
- 天然牙状态变化或修复体替代关系。

通过标准：

- 可按时间、牙齿、事件、周期和来源筛选；
- 图标、来源角标和状态标记一致；
- 日历条目可回到完整事件；
- 单颗牙可查看照片、就医和复诊历史；
- 医院记录不能被个人端覆盖；
- 20,000 个事件、10 年跨度的演示数据下，常用历史视图保持可用；具体性能阈值在实现计划中测定。

## 9. 场景 F：清洁间隔提醒

步骤：

1. 用户开启提醒并选择频率；
2. 完成一次设备记录的清洁；
3. 到达下次提醒时间；
4. 选择稍后提醒；
5. 手动补记一次清洁；
6. 暂停提醒；
7. 删除最近一次清洁记录；
8. 改变时区并重新打开 App。

通过标准：

- 只依据有效的清洁完成事件计算；
- 仅连接、拍照或查看不更新最近清洁时间；
- 通知只描述时间间隔，不评价清洁结果；
- 锁屏不显示牙齿问题、AI 推演或医院信息；
- 补记清楚显示为用户来源；
- 删除、更正、暂停和时区变化后重新计算正确；
- 同一提醒窗口不重复发送；
- 用户能在两步内暂停或关闭。

## 10. 场景 G：安全、隐私和失败恢复

测试：

- 用户 A 尝试访问用户 B 的事件；
- 过期或撤回的分享；
- 非法图片类型和伪装扩展名；
- 超大图片；
- 重复提交；
- 网络中断；
- AI 超时；
- 无设备和无互联网；
- 日志和错误页；
- 通知锁屏显示。

通过标准：

- 越权访问全部被拒绝；
- 撤回后停止新的访问；
- 非法上传被拒绝且不进入分析；
- 错误不暴露密钥、路径、堆栈或个人内容；
- 重试不产生重复业务记录；
- 无网络时仍能拍摄和保存本地事件；
- 日志不包含原图、令牌或对话正文；
- 关键分享、查看、回复、删除和更正有审计记录。

## 11. 验收证据

每个场景保存：

- 测试编号；
- 测试环境；
- 操作步骤；
- 屏幕录制或截图；
- 输入样张编号；
- 实际结果；
- 通过/失败；
- 已知限制；
- 责任人与复测日期。

不得用只有理想路径的录屏替代失败状态验证。

## 12. 阶段出口

### 阶段 0 出口

- 八份规划文档互相一致；
- 硬件未知项清楚；
- 用户确认系统、数据、体验、安全和验收边界；
- 未编写功能代码。

### 阶段 1 入口

- 阶段 0 经用户明确确认；
- 样机协议和接入资料达到调查入口条件；
- 目标 iPhone/iOS 确定；
- 最小样张集可用；
- 安全敏感面的人工评审责任人确定。

阶段 0 通过后也只进入最小可视闭环，医院生产接入和正式模型仍需后续阶段单独确认。
